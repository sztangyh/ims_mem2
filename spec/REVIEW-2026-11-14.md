# spec/ 设计审查（2026-11-14）

> 审查对象：`spec/io_spec.json`（127 行）、`spec/catalog_index.json`（61 行）、`spec/acceptance.md`（49 行）
> 审查视角：**① 作为设计本身；② 作为"替代 numtrace"的契约**——用 numtrace 现有 18 条路由的真实取值语义当尺子。
> 结论先说：**方向对，但 `io_spec.json` 明显过于简化**——它足以表达"意图"，不足以表达"实现"；而且目前有 **3 处与真值/自身验收自相矛盾**。

---

## 1. 结论：从"替代 numtrace"看，简化的四个层级

| 层级 | 现在有什么 | 替代 numtrace 需要什么 | 差距 |
|---|---|---|---|
| **L-A 意图** | ✦ 有：IO 名、来源表、字段白名单、链接目标、目录池 | — | ✅ 这一层做得好 |
| **L-B 绑定** | 字段只有 `name/kind/note`；链接 `expr` 是散文 | 字段要知道**取自哪个 MOC 的哪列**（或哪个函数）；链接要知道**从哪个字段、经什么映射、到哪个键** | ❌ **29 个字段 0 个有 `src`/`fn`** |
| **L-C 形态** | 无 `type`/`form`/`nullable`/`enum` | numtrace 依赖：枚举**码 vs 词**（7 列存码）、Pfx **剥 `K'`**、Bits **`f:{十进制}`**、数值**十进制字符串** | ❌ 无法保证"逐格一致" |
| **L-D 语义** | 无粒度/去重/行数语义 | numtrace 有硬语义：`cnacld` 每 `(ne,lp)` 取**最长字冠**、`clrdsn` 每 `(ne,dsp)` 取**最长 cli**、`rtana` **一键多行是正常**、`MTG=0` 归一 null、`dol≠LOW` 排除 | ❌ 行数/选中语义无法还原 |

一句话：**现在这份 spec 能生成"文档"，生成不出"可运行的替代品"。**

---

## 2. 值得肯定的六处（不是客套，这些方向都对）

1. **`key { external, internal }`** —— 对外人可读（`nsn`）、内部复合键定位（`(ne,pui)`），比"每 MOC 一个对象"成熟得多。
2. **`role_axis`（called/caller/transform）** —— 用一个 IO 扛被叫/主叫/变换三角色，避免拆成三个高度重复的 IO。
3. **`catalog.pool + reach`** —— 目录与对象分离、短字冠/长号码不同触达范围，正是 fzf 式交互的关键。
4. **`dangling` 分"普通→null / 关键链段→resolved"** —— 直击"没查到"与"确实没有"的混淆。
5. **`cache.identity` 与 `version` 正交**（key 是谁、batch 是哪版）—— 与 D59（行号不可用）一致。
6. **`link_expand` 逐跳展开** —— 可停、可缓存、可分页，比一次性拼大树正确。

## 3. 硬缺口（按严重度，全部可机检）

### P0-1 字段没有来源绑定（29/29 缺 `src`/`fn`）

机检结果：**29 个字段全部只有 `kind` + `note`，没有一个 `src` 或 `fn`**。
后果：解释器无法取值；`derived`/`aggregate` 只有散文（"SRTCOST 归一化"、"10 携带者收集取字典序最小"），等于把 `bridge.rs` 里 780 行逻辑重新塞回人的脑子里。

> 修法：`{"name":"tgn","kind":"aggregate","fn":"fn:trunk.tgn","args":["PRATG.TG","PRATKC.TG","TGDSG.TG","TGSRT.TG","SIPTG.TG","SIPIPPAIR.TG","N7TG.TG","V5TG.TGID","V5I.TGID","V5TKC.TGID"]}`，函数实现放代码、契约放 spec。

### P0-2 链接目标有 9 个未声明，且 `expr` 不可执行

机检结果（`to` 里出现但 `io[].name` 里没有）：
```
V5Access(Subscriber.v5i)  PraLink(Trunk.pra_link)  ClrdsnGroup(Trunk.clrdsn)
Rtana / Rt / Srt / Tgsrt(PrefixRoute.chain)  Transform(PrefixRoute.dng)  MgwLink(Mgw.links)
```
后果：① `acceptance.md` 第 2 条"无悬空链接声明"**当前就不成立**；② `expr` 是散文（"TRUNKGP → tg"、"所属网关"、"链式逐跳"），无法生成 join。

### P0-3 没有值形态（`type`/`form`/`nullable`/`enum`）

替代 numtrace 必须逐格一致，而它的前端已经固化了这些形态：

| numtrace 依赖的形态 | 现在的 spec 有无 | 例子 |
|---|---|---|
| 枚举**数字码**（7 列 + trunk `CSF/CDFP`），其余**标签词** | ❌ | `N7TG.CT='1'` vs 标签词 |
| `Pfx` 剥 `K'`（字母/`#` 原样） | ❌ | `K'28811399` → `28811399` |
| `Bits` → `f:{十进制}` | ❌ | `f:5` |
| 业务列一律**字符串**，只有 `ne_id`/`cur_from` 是数字 | ❌ | `"mn":"1003"` |
| `diff`/`shape_id` **恒 null** | 仅 `catalog_index` 提了豁免 | |

### P0-4 没有粒度/去重语义（grain / collapse）

numtrace 的查询里有大量"按键取一条"的隐式规则，spec 里完全没有位置：

- `cnacld`：每 `(ne_id, lp)` 取 **`ORDER BY LENGTH(pfx) DESC` 的第一条**
- `clrdsn`：每 `(ne_id, dsp)` 取 **最长 `cli`**
- `spdnc` 每 `(ne,lp)`、`pfxpro` 每 `(ne,csc,lp)` 去重
- `rtana`：**一键多行是正常形态**（R8），不能去重
- `MTG=0` → 归一 null；`ofc.dol != 'LOW'` → 从"真实中继"排除

> 这些必须落成 `grain`（一个实例由几行构成）+ `collapse`（多行如何收敛：`longest`/`first`/`all`）+ `filters`（行级过滤）。

### P0-5 Trunk 的键缺网元 —— 与自己的 M1 验收自相矛盾

实测桥接真值：
```
bridge_trunk 4,916 行 = 4,916 个 (ne_id, tg) 组合；去重后 tg 只有 2,002 个
⇒ 同一个 tg 跨网元重复 2,914 次
```
spec 写 `"key": {"external":"tg","internal":"tg"}` → 按此实现只有 **2,002** 个对象，
而 `acceptance.md` M1 #1 要求 **4,916**。**两条自己打自己。**

> 修法：`internal: "(ne, tg)"`；`external` 若要单值展示，另立 `display_key`。

### P1-1 缺 `variants`（ASBR 按 DID 的三形态）

桥接层是硬的：`did_filter = ["ESL"]` / `["PRA","ISUP","TUP","SIPPBX"]` / `["V5ST"]`。
spec 只有一句 note（"按 DID 分流"）→ 无法生成三种字段集（`eid·tid` / `isdn·tg` / `v5iid`），而 numtrace 恰恰是**按这三种形态分别查询**的。

### P1-2 缺 per-field 查询能力与排序权重

numtrace 的 SQL 语义需要落到 spec：`eq` / `prefix` / `contains` / `range` / `longest`、`ORDER BY LENGTH(pfx) DESC`、`LIKE 'v%' OR LIKE '%v'`（前缀∪尾部）。
现在只有 `catalog_index.match` 一句全局"策略"，无法表达"哪个字段能怎么查、怎么排"。

### P1-3 缺"覆盖矩阵"→ 无法证明替代完整

numtrace 18 条路由用到的表里，**至少 7 张没有 IO 归属**：
`srtattr`(290 行)、`tgldidx`(5,190)、`tgld`(50)、`sip_ippair`(511)、`iualks`(16)、`iualnk`(64)、`ipaddr`(25)。
没有 `coverage` 段（路由 → 用到的列 → IO 字段 or `legacy_only`），"替代"就只是口号。

### P1-4 缺函数注册表

7 条关键配方（`nsn`/`scc`/`perc`/`kc`/`tg_type`/`tgn`/`direction`/`src`）必须各自有**名字 + 输入输出契约 + 参考实现位置**，否则 spec 与代码永远对不上账。

### P2 其他

| 项 | 问题 |
|---|---|
| spec 无 JSON Schema | `acceptance.md` M0 #1 要求"schema 校验通过"，但 `spec/` 下**没有 schema 文件** → 验收不可执行 |
| `catalog_index` 与 `io_spec` 未对齐 | `prefix` 池写 `"source_moc":["CNACLD.pfx","CLRDSN.pfx","DNC"]`——粒度混用，且 **DNC 没有 `pfx`**（是 `nd`/`dct`）；`cursor:(pool,key,role_scan)` 里 `role_scan` 未定义 |
| `short_cursor: 1~6 位` | 魔法数，且与 numtrace 现行"前缀 ∪ 尾部"匹配冲突；应引用单一来源（`num.rs`）并写明与 `cnacld.minl/maxl` 的关系 |
| **Mgw 无数据源** | ims_mem2 源码里**没有任何 `mgw_*` 表**（只有 AGCF MML 链路）；旧库 `mgw_ne` 有 10 行。M1 却把 Mgw 列为必验项 → 范围炸弹 |
| `Ne` 的行数歧义 | 旧库 `ne` 有 **16** 行（6 AGCF + 10 MGW），spec 与验收都写 6，但没说"仅 AGCF" |
| 缺 error / paging / sort / as_of 契约 | `SERVICE-LAYER.md` 有，spec 里没有回落 |
| `hit_count` 成本 | 每个条目要计数 → 大池上 O(N)，需说明"估算 or 省略" |

## 5. 建议的 spec v2 结构（在现有基础上扩展，不推翻）

```jsonc
{
  "io": [{
    "name": "Trunk",
    "grain": { "key": ["ne", "tg"], "from_rows": "many", "collapse": { "field": "tg", "by": "union", "needed_note": "7 定义型 MOC 的 TG 并集" } },
    "scope": { "ne_types": ["AGCF"] },
    "variants": [],                       // 有 DID 分流的 IO 用：{when:{did:["ESL"]}, fields:[...]}
    "source": [{ "table": "PRATG", "role": "definer", "tg_type": "PRA", "direction_param": "GD" }, ...],   // 结构化，不要 "A∪B∪C" 字符串
    "fields": [{
      "name": "tgn",
      "kind": "aggregate",
      "type": "str",
      "form": "raw",                      // raw | enum_code | enum_label | pfx | bits | json_text | num_str
      "fn": "fn:trunk.tgn",
      "args": ["PRATG.TG", "PRATKC.TG", "TGDSG.TG", "TGSRT.TG", "SIPTG.TG", "SIPIPPAIR.TG", "N7TG.TG", "V5TG.TGID", "V5I.TGID", "V5TKC.TGID"],
      "nullable": true,
      "expose": true,
      "query": { "ops": ["eq"], "index": false }
    }],
    "links": [{
      "field": "serving_mgw",
      "to": "Mgw",
      "card": "n:1",
      "unique": true,
      "key_expr": { "from": "MGW", "map": "ip_port_to_mid", "to_key": "mid" },
      "on_missing": "dangling",           // null | dangling
      "critical": true,                   // 关键链段：客户端必须显示"未解析"
      "paging": null
    }],
    "baseline": { "rows": 4916, "source": "bridge_trunk.ndjson" }
  }],
  "functions": { "fn:trunk.tgn": { "in": "10×键值集", "out": "str", "impl": "bridge.rs:1249-1458" } },
  "coverage":  [{ "route": "/api/trace/callee", "needs": ["cnacld_cur.pfx", "rtana_cur.rsc", ...], "io": "PrefixRoute", "status": "covered|legacy_only" }],
  "errors":   { "codes": ["cursor_expired", "io_not_found", "key_invalid", "dangling_required"] },
  "paging":   { "default": 50, "max": 500, "cursor": "keyset" },
  "schema_version": 2
}
```

**与 v1 的差异**：只加不改 —— `grain/scope/variants/type/form/fn/query/baseline` 是新增；`source` 从字符串拆成表数组；`links` 增加 `key_expr/on_missing/critical`。

## 7. 建议的落地顺序（spec 先行，仍不写业务代码）

1. **补 6 个 IO 声明**（`PraLink`/`ClrdsnGroup`/`Transform`/`V5Access`/`MgwLink` + `chain` 子步）→ 消除 9 处悬空
2. **给 29 个字段加 `src`/`fn`/`type`/`form`**（对照 `bridge.rs` 逐列填，机械工作，可脚本生成草稿）
3. **加 `grain/collapse/filters`**（把 P0-4 的 5 条语义写进去）
4. **加 `coverage`**（18 路由 × 列 → IO 字段；缺失的标 `legacy_only`）
5. **补 `io_spec.schema.json` + `tools/check_io_spec.py`**，把本审查 §3/§4 的每条都变成断言

> 这五步做在 **spec 层**，不碰代码；做完之后 M0 就算真通过，M1 的实现才有明确目标。
